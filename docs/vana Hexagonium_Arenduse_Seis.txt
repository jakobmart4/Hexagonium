2. KAARDISÜSTEEMI ARHITEKTUURSED OTSUSED
========================================================================

2.1 KOLM KINNITATUD ALUSOTSUST
------------------------------------------------------------------------
1) MULTIPLIKAATORID KORRUTUVAD (mitte ei liitu)
   Nt Overclock(2.5) x Bloom(1.25) x Wild(1.20) = 3.75x
   Põhjus: teeb kaardikombinatsioonid põnevaks, mis on mängu tuumidee.
   Risk: power-creep — maandatud allpool kirjeldatud kaitsetega.

2) ÜHTNE SCOPE-SÜSTEEM
   Iga kaart deklareerib: "global" | "hex" | "buildingType"
   Põhjus: vähem koodikordust, uute kaartide lisamine lihtne.

3) KORD AKTIVEERITUD = AKTIIVNE KUNI RUN'I LÕPUNI
   Tsüklilised efektid (Flux Tide, Null Surge) toimuvad kaardi SEES.
   Põhjus: vastab spec'ile, lihtsam olekuhaldus.


2.2 EXPLOIT-KAITSED (TÄHTIS — need on teadlikud otsused)
------------------------------------------------------------------------
EXPLOIT #1: Null Surge + Overclock
  Probleem: NullSurge(3.0) x Overclock(2.5) x Bloom(1.25) x Wild(1.20)
            = 11.25x tootmine, JA Null Surge ajal ignoreeritakse
            sisendeid ning ülekuumenemist ei kontrollita.
            = 10 sekundit täiesti riskivaba 11x tootmist iga 240 sek.

  Lahendus: Null Surge efektifaasis Overclock VÄLISTATAKSE arvutusest
            (asendab, ei korruta). Vastab spec'i sõnastusele
            "Overclock ei aktiveeru Null Surge ajal".

  Tulemus:  11.25x → 4.50x  (kaitse säästis 6.75x)
  Asukoht:  CardManager:ComputeProductionMultiplier(), ERAND 2


EXPLOIT #2: Stable Hex + Overclock
  Probleem: Stable Hex lubab "0% rikke tõenäosust". Kui see kaitseks ka
            Overclocki ülekuumenemise vastu, saaks mängija riskivaba
            2.5x — Overclocki ainus miinus kaoks täielikult.
            See muutuks dominantseks strateegiaks.

  Lahendus: Stable Hex kaitseb AINULT Wild Hexi enda rikete vastu,
            MITTE Overclocki ülekuumenemise vastu.

  Asukoht:  CardManager:HexPreventsFailures() (kommenteeritud koodis)
  MÄRKUS:   See on üherealine muudatus, kui tahad hiljem teisiti.


DIAGNOSTIKA PLAYTESTIKS
  CardManager.EXPLOIT_WARN_THRESHOLD = 6.0
  Kui mõne hoone efektiivne kordaja ületab 6x, logitakse konsooli
  hoiatus koos aktiivsete kaartide nimekirjaga.
  See on TÖÖRIIST, mitte hard-cap — päris tasakaalustamise otsused
  tehakse telemeetria põhjal, mitte ennatlikult.

- Run-süsteem ja meta-progressioon (Hex Seed) puuduvad

6. TÖÖPÕHIMÕTTED, MIDA OLEME JÄRGINUD
========================================================================

- Constants.lua on AINUS koht, kus balance-arvud elavad
- Iga hoone pärib BuildingBase'ist (ühine ühendus/pause/destroy loogika)
- Iga kaart on eraldi moodul selge API-ga (OnActivate/OnTick/
  OnDeactivate + GetProductionModifier/GetDefenseModifier)
- Kaardid ei tunne üksteist otse — nad küsivad CardManager'ilt
  (nt Blessed Hex küsib, kas Mirror World on aktiivne)
- Hooned ei tunne CardManager'it — CardManager seab neile lipud
  (multiplikaatorid, ignoreInputs)
- Iga suurem muudatus testitakse play-režiimis enne edasiminekut
- Exploidid otsitakse ja dokumenteeritakse KOODI SEES, mitte
  ainult vestluses
